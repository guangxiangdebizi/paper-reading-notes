# 知识图谱建设踩坑记录

> 本文档记录搭建与使用 `knowledge_graph/`（Kùzu 论文知识图谱）过程中实际遇到的问题、排查结论与规避方案。
> 环境：Windows 11 + Python 3.12 + kuzu 0.11.3（装在项目外层 `venv/`）。

---

## 1.【非刚需·中级】Kùzu 无法打开路径含中文的数据库

- **日期**：2026-09-18
- **现象**：`kuzu.Database(r"...\非工作项目\paperreading\xxx")` 抛
  `RuntimeError: IO exception: Cannot open file. path: ...\?ǹ?????\... - Error 3: The system cannot find the path specified.`
  报错里的中文变成乱码；即使先用 `os.makedirs` 建好目录，同样失败。
- **排查**：纯 ASCII 路径（如 `C:\Users\26214\AppData\Local\Temp\...`）下同一版本完全正常（DDL/DML/LIST 属性/参数化查询/REL TABLE GROUP 全通过）。报错信息有误导性——"cannot find the path" 实际是**路径编码转换失败**，不是路径不存在。根因在 Kùzu 原生库按 ANSI codepage 转换宽字符路径，与 Python 层无关（Python 自身在同路径读写正常）。
- **规避（已实施）**：
  1. 数据库实体放纯 ASCII 路径 `C:\Users\26214\paperreading_kgdb\graph.kuzu`；
  2. 仓库内 `knowledge_graph/db` 是指向该目录的 junction（目录联接），在仓库里能直接看到库文件；
  3. 脚本内部一律使用 ASCII 实体路径（见 `build_graph.py` / `query.py` 顶部常量）；
  4. **换机器/换路径时**：改这两个脚本里的 `DB_PARENT` / `DB_FILE` 常量即可；`C:\Users\26214\paperreading_kgdb` 这个目录不要删（junction 目标）。
- **备注**：junction 不入库（已在 `.gitignore` 排除），clone 后跑一次 `build_graph.py` 会自动建库；如需 junction 视图，用第 3 条里的 Python 方式创建。

## 2.【非刚需·中级】Kùzu 0.11 的 Cypher 是 Neo4j 方言子集，7 处写法差异

- **日期**：2026-09-18
- **现象**：以下在 Neo4j 可用的写法，在 Kùzu 0.11 报 Parser / Binder / Catalog 异常：

| # | Neo4j 写法（不可用） | Kùzu 可用写法 | 报错 |
|---|---|---|---|
| 1 | `CREATE (n:Label $mapParam)` | 逐字段命名参数 `CREATE (n:Label {a:$a, b:$b})` | Parser exception: Invalid input `<$` |
| 2 | `MATCH (x {key:$param})` | `MATCH (x) WHERE x.key = $param` | Parser exception |
| 3 | `type(r)` | `label(r)` | Catalog exception: function TYPE does not exist |
| 4 | `[x IN collect(y)][0..3]` | `list_slice(collect(y), 1, 3)` | Parser exception |
| 5 | `[n IN nodes(path) \| n.id]` | `list_transform(nodes(path), n -> n.id)` | Binder exception: Variable n is not in scope |
| 6 | `RETURN expr AS 路线/家族`（别名含 `/`） | 别名避免特殊字符 | Parser exception: mismatched input '/' |
| 7 | `Database(目录路径)` | `Database(单文件路径)`，传已存在目录会报错 | Database path cannot be a directory |

- **排查结论**：Kùzu 自称 openCypher 兼容，但实现是子集，官方文档未集中列出差异；报错的 offset 指向位置常与真实根因（方言不支持）有偏差，容易误判成自己的查询逻辑写错。
- **规避**：`query.py` 的 `--demo` 内置 12 条查询、`build_graph.py` 的全部 DDL/DML 都是已跑通的 Kùzu 写法，新写 Cypher 报 parser 错时先对照上表，再参考这两处。

## 3.【非刚需·初级】Git Bash 下 `cmd /c mklink /J` 对含中文的路径失败

- **日期**：2026-09-18
- **现象**：`cmd //c "mklink /J <含中文的link路径> <target>"` 报「文件或目录不是语法正确的」（link 路径里的中文在 codepage 转换中损坏）。
- **规避**：改用 Python `_winapi.CreateJunction(target, link)`（走宽字符 API，可靠）。注意两点：target 目录必须先存在；清理时先删 junction（`os.rmdir`）再删实体目录，避免误删数据。
- 本项目移动 `knowledge_graph/` 进仓库时即按此方式重建 junction。

## 4.【非刚需·初级】建图数据的两处一致性坑（loader 已修复）

- **日期**：2026-09-18
- **现象与根因**：
  1. `BELONGS_TO` 的主线序号全部落成 0——单篇 YAML 片段里字段名是 `order`，loader 读的是 `seq`；
  2. Dataset 节点重复（`ImageNet-1K` / `ImageNet-1k` 各建一个）——不同论文片段对同一数据集大小写写法不一致。
- **规避（已实施于 `build_graph.py`）**：loader 兼容 `order`/`seq` 两个字段名；Dataset 按「小写 + 去空格」归一化去重，并合并互补信息（已有条目缺 scale 时用新条目的补上）。
- **提示**：后续新增片段时，同一数据集请沿用已有写法（`ImageNet-1K`、`ImageNet-21K`、`COCO`、`ADE20K` 等），可减少归一化负担。

## 5.【非刚需·初级】Windows 控制台中文输出乱码

- **日期**：2026-09-18
- **现象**：直接在 Git Bash / PowerShell 里用内联 Python 打印中文，输出为乱码（codepage 非 UTF-8）。
- **规避**：`query.py` 已在入口处 `sys.stdout.reconfigure(encoding="utf-8")`，用该脚本查询显示正常；自己写内联 Python 时需手动加这一行。**数据本身是完整 UTF-8，乱码只是显示问题，不影响库内容。**
